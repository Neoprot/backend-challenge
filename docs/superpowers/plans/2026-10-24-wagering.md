# Plano de implementação — processador distribuído de apostas

> **For agentic workers:** REQUIRED SUB-SKILL: Use `execute-plan-tdd` to implement this plan task-by-task. This skill applies TDD by default, performs spec-compliance review before code-quality review, and may dispatch a fresh subagent for isolated tasks when beneficial.

**Objetivo:** entregar todos os requisitos obrigatórios do README, com Keycloak e TDD obrigatório, demonstrando correção financeira em três ou mais processos.

**Arquitetura:** domínio encapsulado, casos de uso compartilhados por HTTP/SQS e adaptadores de infraestrutura. Transação PostgreSQL com lock por wallet, inbox/outbox e ledger imutável. Workers recuperáveis e autorização por identidade do provedor.

**Stack:** Bun 1.x, TypeScript estrito, NestJS, MikroORM, PostgreSQL, SQS/LocalStack, Docker Compose e Keycloak.

**Especificação:** `docs/superpowers/specs/2026-10-24-wagering-design.md`.

## Execução e limites

Executar uma tarefa por vez, em branch `codex/wagering-processor`, em workspace isolado. Não alterar o fork nem usar seu código. Não iniciar implementação antes da aprovação deste plano. Não publicar, criar PR ou fazer merge como efeito do planejamento.

O ambiente observado em 24/10/2026 tem Bun 1.3.11 e Docker CLI 29.3.0; o daemon do contexto desktop-linux não estava disponível. Antes de IT, iniciar Docker Desktop e confirmar que o servidor responde. Falha de ambiente não conta como RED de negócio e não autoriza substituir containers por mocks.

As versões exatas dos pacotes e imagens serão resolvidas e fixadas durante o bootstrap, com verificação dos requisitos de runtime e smoke test conjunto. Não usar tags `latest` nem intervalos flutuantes. Bun local 1.3.11 é o ponto de partida, sujeito ao smoke test, permanecendo obrigatoriamente em 1.x. Todos os pacotes MikroORM devem ter a mesma versão; pacotes NestJS devem pertencer à mesma versão principal.

## Regra de TDD — obrigatória em cada tarefa funcional

1. **RED:** escrever o teste do próximo comportamento e executá-lo. Registrar comando, falha e requisito; confirmar que a falha não é causada por indisponibilidade do ambiente.
2. **GREEN:** implementar o menor incremento que satisfaça o teste. Não antecipar regras de tarefas posteriores.
3. **REFACTOR:** remover duplicação e melhorar limites sem alterar comportamento; executar novamente os testes afetados e o typecheck.
4. **Revisão:** primeiro verificar conformidade com especificação/README; depois qualidade do código e dos testes. Corrigir achados antes de avançar.
5. **Registro:** atualizar `docs/superpowers/plans/checkpoint-plan-2026-10-24-wagering.md` e criar commit específico, incluindo somente arquivos da tarefa.

Testes unitários são obrigatórios para regras, políticas e estados. IT são obrigatórios para qualquer mudança em banco, HTTP, SQS, autenticação ou coordenação entre processos. Uma correção começa pelo teste de regressão. Não remover assertions, relaxar constraints nem adicionar skip para obter GREEN. Configuração mecânica e documentação não precisam de testes artificiais, mas exigem validação apropriada.

Tarefas com IT bloqueados ficam PARTIAL/BLOCKED, nunca COMPLETE. Antes de declarar entrega, todas as suítes obrigatórias precisam executar e passar. Contagem de testes ou cobertura de linhas não substitui verificação dos invariantes.

## Comandos de verificação

Os scripts abaixo serão criados no bootstrap. `rtk` é o prefixo de execução no ambiente do usuário, não dependência do projeto nem do container.

```json
{
  "scripts": {
    "start": "bun src/bootstrap/main.ts",
    "typecheck": "tsc --noEmit",
    "test:unit": "bun test test/unit",
    "test:it": "bun scripts/run-integration.ts",
    "test:concurrency": "bun scripts/run-concurrency.ts",
    "migration:up": "bun scripts/migrate.ts up",
    "migration:down": "bun scripts/migrate.ts down",
    "seed:local": "bun scripts/seed-local.ts"
  }
}
```

O runner de IT verifica serviços disponíveis, exige banco e filas exclusivos de teste, executa `bun test test/integration --timeout 60000` e propaga seu exit code. O runner de concorrência executa `bun test test/concurrency --timeout 120000` com três processos reais. Nenhum runner pode ignorar testes quando o Docker estiver indisponível. Cada arquivo de teste deve falhar se seu setup obrigatório falhar.
